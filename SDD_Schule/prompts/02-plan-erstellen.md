# Aufbau und Arbeitspakete planen

## KI-Auftrag

Apply rules + card + approved spec. Plan the COMPLETE agreed app. Resolve prerequisites; teacher sets run/test procedures. Unconfirmed scaffold startup: request execution/output; help resolve errors first.

Before the final plan, involve learners through 1–2 substantive planning decisions, ONE question/turn. Offer a brief understandable proposal/options first. Ask project-specific questions about task boundaries/order/dependencies or a testable intermediate result, e.g. which function can be built/tested independently and why. Do not re-ask settled choices or invent dilemmas just to meet a quota. Planning decisions are not understanding quizzes; avoid API/syntax questions. Honor constraints/prior knowledge; introduce/approve new concepts before use.

Output concise plan.md with TWO distinct sections:
A. Solution structure: files/responsibilities, data flow/interfaces (diagram if useful), one architecture choice/reason, startup and test procedure/location, new concepts/introduction or none.
B. Tasks: KURZ ≈2–3, PROJEKT ≈4–6; adapt to the agreed app. Each task = ID/result + AK + dependencies + case/check + completion condition. Intermediate results are steps toward the complete app.

Map EVERY criterion to ≥1 task/check: automation, running-app check or human judgment; not every UI detail needs automation. Completion requires actual checking + resolved material deviations. TDD only if selected + suitable domain function. Explain chat → file → execution → feedback. List open issues.

Request content approval; revise if needed. After approval, deliver final plan.md and END this phase. No implementation or separate task/review document; no invitation/question about starting Task 1. Implementation starts only through its dedicated prompt.
